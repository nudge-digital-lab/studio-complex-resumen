Cómo trabajamos juntos cuando hay código

Un solo repositorio por proyecto en GitHub, los dos con acceso, y nadie toca la versión publicada sin que el otro lo vea. Así cualquiera puede hacer un cambio sin pisar el trabajo del otro, y siempre sabemos qué cambió, quién lo hizo y cómo volver atrás.

El recorrido de un cambio

01

Traer lo último

Antes de empezar, bajar lo que haya cambiado en GitHub.

02

Abrir una rama

Una copia aparte para este cambio, con nombre: seba/precios.

03

Trabajar y guardar

Cada avance es un commit con un mensaje que diga qué y por qué.

04

Subir y pedir revisión

Push de la rama y un Pull Request en GitHub.

05

El otro revisa

En el CRM, Vercel arma una versión de prueba de ese PR para verlo andando.

06

Merge y publicación

Aprobado, se une a la rama principal y recién ahí se publica.

Tus dos diagramas

El del CRM Correcto

Rama de cada uno → PR → rama principal → Vercel es exactamente el flujo. Dos precisiones: la rama principal del CRM se llama master, no main, y Vercel ya publica solo cada vez que algo entra a master. Por eso nada entra sin PR.

El de "repo de tu socio" Un ajuste

No hay un repo mío y uno tuyo: hay uno solo, compartido, y los dos somos colaboradores. No hace falta copiar el repositorio (fork). Clonás el mismo, trabajás en tu rama y el resto de tu esquema queda igual.

El recorrido es el mismo. Lo único que cambia es el último paso.

El día a día, en comandos

Lo mismo se puede hacer con botones en GitHub Desktop o en VS Code. Esto es lo que pasa por debajo.

# 1. Traer lo último (en el CRM la rama principal es master) git switch main git pull # 2. Abrir una rama para este cambio git switch -c seba/precios-servicios # 3. Trabajar y guardar cada avance git add . git commit -m "Precios en la página de Tiendas" # 4. Subir la rama y abrir el Pull Request en GitHub git push -u origin seba/precios-servicios

Reglas cortas

  • Nadie trabaja directo sobre la rama principal. Toda la vida, rama y PR.
  • Una rama por cambio, con quién y qué: jorge/whois, seba/seo-home.
  • PR chicos: un tema por vez. Se revisan en el día y se revisan de verdad.
  • Solo se publica desde la rama principal, nunca desde una rama.
  • Contraseñas y claves nunca van al repositorio: van en .env, que Git ignora, o en Vercel.
  • Si los dos tocamos lo mismo, Git avisa (conflicto). Se trae lo último a la rama, se eligen las líneas correctas y se prueba antes del merge.

Para arrancar

  1. Pasame tu usuario de GitHub y te sumo como colaborador a la web y al CRM.
  2. Aceptá la invitación que te llega por mail.
  3. Instalá Git y GitHub Desktop (o VS Code) y cloná los dos repositorios.
  4. Hacé un primer cambio chico con su rama y su PR, y lo revisamos juntos.
